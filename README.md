# รายงานสรุปภาพรวมและสถาปัตยกรรม — MeBuddy ผู้ช่วย AI บน Discord

> เอกสารนี้อธิบายการตัดสินใจเชิงวิศวกรรมของระบบ เพื่อใช้อ้างอิงและเผยแพร่ต่อสาธารณะ โดยไม่เปิดเผยซอร์สโค้ด ข้อมูลผู้ใช้ ค่าตั้งค่า ตัวระบุของแอปพลิเคชัน หรือรายละเอียดที่ช่วยให้เข้าถึงระบบได้

## 1. ภาพรวม

MeBuddy เป็นผู้ช่วย AI ประจำคอมมูนิตี้ที่ใช้งานผ่าน Discord สมาชิกเรียกใช้ด้วยคำสั่ง เปิดห้องคุยส่วนตัวเพื่อสนทนาต่อเนื่อง และซื้อโควตาการใช้งานเป็นแพ็กเกจ

พัฒนาที่ ME PROMPT TECHNOLOGY เมื่อเดือนตุลาคม 2026

## 2. โจทย์ที่กำหนดรูปร่างของระบบ

ระบบที่เรียกโมเดล AI แล้วคิดเงินมีข้อจำกัดที่ไม่เหมือนระบบทั่วไปสองข้อ

1. **งานหนึ่งชิ้นใช้เวลานาน** ไม่จบภายในหนึ่ง Request
2. **แต่ละครั้งมีต้นทุนจริง** จึงต้องนับและจำกัดได้

ความผิดพลาดที่ตามมาจึงมีสองทิศทางที่แย่พอกัน คือผู้ใช้จ่ายแล้วไม่ได้ผลลัพธ์ กับระบบประมวลผลให้ฟรีเพราะนับโควตาพลาด การออกแบบทั้งหมดจึงวนรอบคำถามเดียวว่า **โควตาถูกตัดตอนไหน และตัดซ้ำได้หรือไม่**

## 3. จองโควตาพร้อมสร้างงานในธุรกรรมเดียว

การตัดโควตาและการสร้างงานต้องเกิดขึ้นพร้อมกันหรือไม่เกิดเลย ระบบจึงครอบทั้งสองอย่างไว้ใน Transaction เดียวของฐานข้อมูล

ถ้าแยกกันทำ จะเกิดสองกรณีที่พบได้จริง

- ตัดโควตาแล้วสร้างงานไม่สำเร็จ — ผู้ใช้เสียโควตาฟรี
- สร้างงานแล้วตัดโควตาไม่สำเร็จ — ระบบทำงานให้โดยไม่คิดเงิน

ทั้งสองกรณีหายไปเมื่อทำในธุรกรรมเดียว

## 4. Retry ที่ไม่เริ่มประมวลผลใหม่

นี่คือการตัดสินใจที่สำคัญที่สุดของระบบ

**การลองใหม่ในขั้นอ่านผลลัพธ์หรือส่งผลกลับ จะไม่เริ่มการประมวลผลใหม่ และไม่กินโควตาเพิ่ม**

เหตุผลคือขั้นตอนที่ล้มบ่อยที่สุดไม่ใช่การประมวลผลเอง แต่เป็นขั้นส่งผลกลับไปหาผู้ใช้ ซึ่งขึ้นกับเครือข่ายและบริการภายนอก ถ้าออกแบบให้ retry ทั้งก้อน ผู้ใช้จะถูกหักโควตาซ้ำจากงานที่ระบบทำเสร็จไปแล้ว และยิ่งเครือข่ายแย่ ยิ่งถูกหักหนัก

หลักทั่วไปที่ได้จากข้อนี้คือ **แยกขั้นที่มีต้นทุนออกจากขั้นที่ล้มบ่อย** แล้วทำให้ขั้นที่ล้มบ่อยทำซ้ำได้อย่างปลอดภัย

## 5. กันคำขอซ้ำ และกู้คืนงานค้าง

- **กันคำขอซ้ำตั้งแต่ต้นทาง** เพราะผู้ใช้กดซ้ำเสมอเมื่อระบบตอบช้า
- **Claim/Lease สำหรับงานที่ถูกหยิบไปทำ** งานที่ตัวประมวลผลหยิบไปแล้วแต่ค้างกลางทาง เช่น โปรเซสดับ จะถูกกู้คืนได้ แทนที่จะค้างถาวร หรือถูกหยิบซ้ำโดยตัวประมวลผลสองตัวพร้อมกัน

## 6. แยกตัวประมวลผลออกจากบอท และให้สิทธิ์เท่าที่จำเป็น

ตัวประมวลผลงานแยกจากตัวบอท และได้รับเฉพาะความสามารถที่งานนั้นต้องใช้ ไม่ได้รับสิทธิ์ทั้งหมดของระบบ

ข้อดีคือเมื่อส่วนใดส่วนหนึ่งถูกบุกรุกหรือทำงานผิดพลาด ขอบเขตความเสียหายถูกจำกัดไว้ล่วงหน้า และทั้งสองส่วนปรับขนาดแยกกันได้ตามภาระงานที่ต่างกัน

## 7. โควตา การเก็บเงิน และการตรวจสอบย้อนหลัง

- เจ้าของระบบตั้งสิทธิ์ เพดานการใช้งาน สร้างแพ็กเกจ และมอบโควตาได้ โดยทุกการกระทำมีบันทึกตรวจสอบ
- สมาชิกซื้อแพ็กเกจเองได้ พร้อมยืนยันเงื่อนไขก่อนชำระ
- คำสั่งและผลลัพธ์ของทุกคำขอถูกเก็บไว้ตามค่าเริ่มต้น เพื่อให้ตรวจย้อนหลังได้ และสมาชิกอ่านประวัติห้องที่ตนร่วมได้

การเก็บประวัติเป็นเรื่องที่ต้องบอกผู้ใช้ให้ชัดตั้งแต่ต้น ไม่ใช่สิ่งที่ซ่อนไว้ในเงื่อนไข

## 8. เลือกโมเดลตามประเภทงาน

เมื่อเปิดโหมดอัตโนมัติ ระบบจะจัดประเภทคำขอก่อน แล้วจึงเลือกโมเดลให้เหมาะกับงานนั้น เช่น งานสนทนาทั่วไป งานเขียนโค้ด งานวิเคราะห์ที่ต้องใช้การให้เหตุผลมาก หรืองานสร้างภาพ

เหตุผลคือโมเดลที่เก่งที่สุดไม่ใช่โมเดลที่คุ้มที่สุดสำหรับทุกงาน การใช้ตัวเดียวกับทุกอย่างคือการจ่ายแพงเกินจำเป็นในงานง่าย และได้ผลไม่ดีพอในงานยาก
